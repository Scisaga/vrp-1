# vrp-1 架构

工作台的页面、场景切换和规划/执行操作关系见 [workbench.md](workbench.md)。应用层扩展以 `app.proto` 为准，不改变计算核心的依赖和 I/O 边界。

离线底图应用层组件 `vrp-basemap` 负责 PMTiles 区域提取与验证，显示资源由服务内置托管；与计算路网、评分和冻结输入独立。共享地图契约位于 `proto/vrp/maps/v1/maps.proto`，使用与验收见 [offline-basemaps.md](offline-basemaps.md)。

## 1. 定位

vrp-1 是 PsiAI 的车辆路径（VRP）引擎，用 Rust 实现，取代 vrp-0（Java / Quarkus / OptaPlanner）。目标同时包含可嵌入的计算内核、CLI，以及可独立部署的服务与前端。

**纯计算边界限定在 `vrp-core` 与模型转换层**：输入一份完整的求解请求（问题、矩阵、参数），输出方案、分数和解释。进程管理、网络、持久化与界面由外层组件负责，不进入核心。当前已有库、CLI、本地隔离 Worker、独立 HTTP 服务和随二进制内嵌的浏览器工作台。运行见 [server.md](server.md)，产品边界见 [standalone.md](standalone.md)。

**目标规模。** 单次任务不超过 1000 单、200 车，扩展目标是大量独立任务的并发执行。单个超大场景及其跨节点分解不在需求范围内。这里定义设计与验收范围，接口的运行时校验仍以契约和实现为准。

**首版业务范围。** 同时覆盖出发前规划和车辆出发后的实时重排。继续优化、场景变更后的重新求解、执行中的实时重排是三种不同操作。已实现执行事实、锁、实际载荷、自动触发及生效计划；实现语义、测试与边界见 [realtime-planning.md](realtime-planning.md)。默认人工确认方案，可配置自动采用；行驶中允许建议改变下一站。

独立工作台内嵌 MapLibre，默认离线底图优先，缺包时以在线 OSM 底图过渡，也可配置自有瓦片/PMTiles。应用层提供通用任务中心和路网包管理：根据场景范围选择 Geofabrik 全球目录中新增下载量较小的包组合，复用本地数据，通过独立 Rust 路网进程准备矩阵及道路折线。地图下载、PBF 处理、索引和文件缓存不进入求解内核。调用方也可提供完整矩阵和外部道路折线。来源、坐标处理、路网快照和质量摘要留在应用协议。见 [开放地图与历史场景](maps-and-import.md) 和 [路网与通用任务](geo-tasks.md)。vrp-1 不做 v1 兼容模式，也不读写 vrp-0 的 `data/` 目录。

## 2. 仓库结构

```text
vrp-1/
├─ proto/vrp/engine/v1/engine.proto   求解请求、结果（契约的唯一定义）
├─ proto/vrp/worker/v1/worker.proto   本地子进程 IPC
├─ proto/vrp/app/v1/app.proto         独立应用的场景版本、任务、HTTP 与进度事件契约
├─ crates/
│  ├─ vrp-proto       由 .proto 生成的 Rust 类型（build.rs 用 protox，无需 protoc）
│  ├─ vrp-core        内部表示、评分、多线程搜索；只依赖标准库，无 I/O、无 async
│  ├─ vrp-model       校验、协议转换、矩阵兜底估算，以及共享额度的执行入口
│  ├─ vrp-geo         PBF 道路提取、范围和目录匹配、空间索引、路网矩阵及路径
│  ├─ vrp-import-v1   把 vrp-0 的 JSON 转成 v2 请求（开发工具，不是兼容模式）
│  ├─ vrp-worker      本地 supervisor、进度/取消 IPC、进程隔离及内存限制
│  ├─ vrp-server      独立 HTTP API、SQLite、执行投影、重排/采用、本机调度
│  └─ vrp-cli         命令行：import-v1 / eval / bench / solve / solve-isolated
├─ web/              原生 ES module、CSS、HTML，构建时内嵌，无 CDN/Node 运行依赖
└─ docs/
   ├─ architecture.md       本文
   ├─ constraints-v2.md     评分语义
   ├─ standalone.md         产品方案与实施阶段
   └─ server.md             已实现的独立任务服务使用说明
```

依赖方向：`vrp-cli` → `vrp-import-v1` → `vrp-model` → `vrp-core` / `vrp-proto`；`vrp-server` → `vrp-worker` / `vrp-model` / `vrp-proto` / `vrp-geo`。`vrp-core` 不依赖任何协议层的 crate。ProtoJSON 也由 `.proto` 生成，服务层不维护另一套求解 DTO。

## 3. 数据流

```text
SolveRequest（protobuf）
  │  vrp-model：校验下标与取值、补齐未知边、编译
  ▼
vrp_core::Problem（下标化、整数化、按 agent 预计算候选集合）
  │  vrp-core：构造初解 → 搜索（评分走增量路径）
  ▼
vrp_core::Solution + 全量评分（oracle）生成解释
  │  vrp-model：转回 proto
  ▼
SolveResult
```

## 4. 契约要点

**单位和引用。** 契约的权威定义见 `engine.proto`，要点如下：
- 时间是相对 Horizon 起点的秒，引擎内部不做日历和时区计算；
- 实体之间用下标引用，id 只用于对外标识；
- 容量和需求是整数，单位由生产方声明。

**矩阵。** 每个车型 profile 一张 n×n 矩阵：
- 时长（秒）和距离（米）各是一个小端 u32 数组，以 `bytes` 传输。对比之下，vrp-0 的 JSON 矩阵每个条目约 117 字节，这里是 8 字节；
- 两个保留值：`0xFFFFFFFF` 表示不可达，`0xFFFFFFFE` 表示未知；
- 可选的每边 1 字节来源标记：实测、缓存、模型估算、兜底估算。方案经过的非实测边会列进结果，调用方可优先校正这些边；
- 估算边排班时按 `estimate_buffer` 放大时长，给估算误差留余量，行驶成本仍按原值（constraints-v2 第 1 节）。

**兜底估算。** 未知边由 vrp-1 在编译阶段用确定性的几何估算补齐：曼哈顿或大圆距离，乘绕行系数，再按距离分段车速换算时长。估算参数写在请求里，保证归档可以复现。

**热启动。** 请求可以带初始解，用于继续优化或场景修改后重新求解。初始解只提供搜索起点，不保证计划稳定，也不能代替实时重排需要的执行事实、锁和货物状态。

**求解档位。** `SolveOptions.preset` 提供三档，未指定时选默认档：

| 档位 | 总求解时限 | 连续无改进停止时间 |
|---|---|---|
| `FAST`（默认） | 30 秒 | 不设置 |
| `STANDARD` | 120 秒 | 不设置 |
| `DEEP` | 不设置 | 300 秒 |

请求可以用正值 `time_limit_ms`、`unimproved_stop_ms` 覆盖对应默认值，0 表示沿用档位设置。两项都启用时，任一条件达到即停止；深度档的 300 秒是连续无改进时间，可以另设总时限。计时从实际开始求解时算起，不包含排队、地图数据准备和请求编译。无改进时间只在任务的全局最佳分数严格改善时重置，等分方案不重置，多线程共享这一计时。

`vrp-model` 编译请求时解析档位和覆盖参数，保留实际时限、线程数与 seed，供搜索器使用。

## 5. 内部表示与性能原则

- **结构数组（SoA）+ 整数运算。** 热路径不分配内存、不用浮点。浮点只出现在少数路线级汇总里（例如负载比例），只用 IEEE 基本运算，不用 `pow` 等库函数。
- **编译期预计算。**
  - 工单 × agent 的静态违反标记：技能、资质、网点、日期；
  - 候选 agent 集合：仅固定工单限制原 agent，其余保留全部候选，规则见 constraints-v2 第 3 节；
  - 关联对、依赖对的邻接表。
- **路线级增量评分。** 每条路线缓存一份汇总（时间表、载荷峰值、各约束匹配量）。没有启用工单时序依赖时，一次移动只重算被修改的路线和关联对。启用依赖时，先对路线顺序与业务依赖组成的图传播最早开始时间，再重算被修改或等待时间发生变化的路线；跨资源的下游等待也必须计入，不能局限于移动直接涉及的两条路线。增量状态复用图和时间数组；独立 oracle 另行计算时间表，差分测试覆盖多前置、跨资源传播、缺失前置和路线顺序产生的环。
- **全量评分（oracle）独立实现。** 逐条约束按定义直接计算，代码追求清晰而不是速度，用于：
  - 和增量评分做差分测试；
  - 生成最终解释。
- **确定性。** 随机数由请求里的 seed 驱动；多线程时每个线程的 seed 由主 seed 派生。归档能恢复相同输入和参数；按墙钟时间停止及多线程调度不保证每次得到完全相同的方案。

## 6. 求解

- **初始方案。** 使用经过校验的热启动方案；未提供时先放入固定工单，再逐张尝试最优位置插入。不同线程使用不同工单顺序。当前采用贪心插入，regret-k 待基准结果支持后再评估。
- **局部搜索。** relocate（包括派入和取消非固定工单）、swap、路线内片段反转、Or-opt（连续 1～3 单移动），使用路线级增量评分。Late Acceptance 允许暂时退步，始终单独保留全局最佳方案。
- **候选与扰动。** 每张工单按矩阵缓存最多 16 个候选，80% 概率尝试候选引导、20% 保留全域探索；周期性交替进行双桥扰动和基础移除/修复。可选普通近邻、alpha-nearness，或 alpha 加可变深度 k-opt；默认保留普通近邻，新增策略由请求显式选择。Alpha 包含最小 1-tree、节点罚值次梯度优化和所有边的敏感度计算。k-opt 包含连续换边、非连续换边与子环修补；删除原路线边的总数（含修补）默认最多 5，可设 2～12。实现边界、来源论文及发布年月、对照结果见 [search.md](search.md)，待实现的算子与算法见 [search-roadmap.md](search-roadmap.md)；不等同于完整 LKH-3，尚无完整 SISR 或常数时间路线片段评分。
- **停止。** 总时限、全局无改进时限或调用方取消，任一达到即停止；候选评估之间协作检查，返回已记录的最佳方案。空问题或没有 agent 的问题可立即完成。输出说明停止原因，并用独立 oracle 复核最终分数；不承诺全局最优或必然满足全部硬约束。
- **单任务多线程。** 支持按请求设置 `threads`（0 视为 1），以不同 seed 并行搜索。各线程共享只读问题数据，分别持有路线和评分状态，定期交流全局最佳方案；单线程仅作为正确性和性能对照。
- **机器线程额度。** 所有运行任务的求解线程合计不得超过 `max(1, floor(C × M))`，C 为部署环境分配的可用逻辑 CPU 数，M 为可配置倍数，默认 1.0。示例：8 核、M=1.8 时为 14 个线程额度。额度不足时排队，不能让每个任务分别占满机器额度。同一机器上的多个 worker / 引擎版本必须共享预算或事先切分配额。
- **进程内执行入口。** `vrp_model::Executor` 可由多个调用线程共享：先申请任务所需的全部线程额度，再编译矩阵并求解；不足时按 FIFO 排队，队列容量由宿主配置，队满立即返回 `QueueFull`。超出总预算的单任务直接拒绝；排队取消返回 `Cancelled`，搜索中取消则返回当前最佳方案。任务返回、编译失败或异常展开时自动释放额度。宿主应复用同一个 Executor，并限制提交线程数；这是同步库接口，不会自行创建排队线程，也不提供跨进程额度协调。

## 7. 运行形态

- **CLI。** 本地开发、基准测试、离线批处理。`vrp solve <请求.pb 或 v1.json> <新的结果.pb>` 运行求解，已有结果文件不会覆盖；支持 `--preset fast|standard|deep`、`--time-limit-ms`、`--unimproved-ms`、`--threads`、`--seed` 和 `--cpu-multiplier`。倍数也可由 `VRP_CPU_MULTIPLIER` 指定，命令行优先，默认 1.0。CLI 按当前进程可用逻辑 CPU 数校验请求线程数；多个独立 CLI 进程之间的总额度协调属于宿主/worker 的职责。库调用可用 `AtomicBool` 取消；CLI 的信号处理与 JSONL 进度尚待 worker 接入时实现。
- **worker。** 已实现本地 supervisor 与一次性子进程，CLI 用 `solve-isolated` 调用；stdin/stdout 使用 `worker.proto` 定义的带长度 protobuf 帧，接入进度、协作取消、超时强制回收及 Windows Job Object / Linux RLIMIT_AS 资源限制。子进程在取得共享额度后启动，回收完毕后归还额度。详见 [worker.md](worker.md)。
- **独立服务。** `vrp-server` 提供多场景版本、任务提交/查询/取消/下载、幂等、SQLite 持久化、有界 FIFO 队列、SSE，以及执行事件、历史快照、人工/自动采用和车辆确认。内部复用 Supervisor，支持 Ctrl+C / Linux SIGTERM 排空。启动后访问 `/` 使用内嵌工作台。默认本机访问，对外监听要求 Bearer 令牌。详见 [server.md](server.md)。
- **库。** 以后需要时再提供 Python 绑定。

## 8. 测试与基准

- **跨版本完整求解评测。** [多场景评测方法](evaluation.md)先核对共同搜索目标，再串行测量指定 vrp-0 / OptaPlanner 与 vrp-1 的质量、时间及资源；共同语义排名和新版能力验收分开。工具位于 `benchmarks/`，真实首轮汇总见[完整报告](benchmarks/round-1/report.md)。它独立于下面的评分吞吐基准，不改变 core 评分语义或业务契约。
- **单元测试。** 每条约束都有手工构造的小场景。
- **差分测试。** 随机方案加随机移动，增量评分必须与 oracle 完全一致。
- **基准。** 在项目根目录执行 `vrp bench`，默认从 `./corpus` 读取 vrp-0 场景；目录优先级为 `--corpus` > `VRP_CORPUS_DIR` > `./corpus`。报告：
  - 导入警告、矩阵覆盖率；
  - v1 记录的分数与 v2 重算的分数；
  - 评分吞吐，并在真实数据上抽查增量评分与 oracle 是否一致。

  `corpus/` 保留在项目文件夹中，除 `.gitkeep` 外的内容由 `.gitignore` 排除。私有语料和由它生成的文件不得提交。已从本地旧仓库整理历史案例，目录、来源哈希、候选配对和校验记录保存在私有索引中，工具说明见 [corpus.md](corpus.md)。存在 `bench.txt` 时只基准其中的明确请求，避免把结果、损坏原件与重复文件混作问题；空清单或所选请求失败不视为一次成功的基准测试。
- **v1 结果文件不能直接当问题用。** vrp-0 在求解前后会改写输入：
  - 把 agent 的 `shift_start_time` 改成路线结束前后的时刻；
  - 求解后替换矩阵条目；
  - 对 AUX 场景把已指派工单的时间窗改成半天档（`updateMinStartTimeAndMaxEndTime` / `rearrange`）。

  因此对比时用请求文件做问题，结果文件只提供指派：`vrp eval <请求.json> --solution <结果.json> [--matrix <结果.json>]`。
