# 执行中的实时重排：首版需求与设计

状态：2026-10-31 已实现 engine/app 协议、执行投影与评分、持久化事件、自动重排、人工/自动采用、车辆确认及内嵌工作台，并以合成动态事件和真实浏览器验证。历史业务语料已拷入 `corpus/`，继续用于静态回归。外部契约仅以 `proto/` 为准；现场动态数据的业务验收仍需另行进行。

## 1. 术语与已确定决策

- **继续优化**：问题不变，从已有终态结果热启动并新建求解任务。业务版本或执行事实/生效计划基准已变时拒绝，分别转入重新规划或实时重排。
- **重新求解 / 重新规划**：场景数据改变后，针对新问题重新计算，可以使用旧方案作为初始解。
- **执行中的实时重排 / 连续求解**：车辆已经出发，持续接收业务与执行事件，在事实和承诺约束下调整剩余任务。这是首版业务重点，不能用前两项代替。
- **采用**：将候选方案变成生效计划。默认人工确认，同时提供可配置的自动采用；两种模式执行相同的版本、可执行性和锁定校验。
- **行驶中允许建议改道**：车辆正在前往 A 时，可以提出先去 B、再去 A 的候选方案，最终仍按采用模式生效。不能默认将行驶中的下一站锁死；正在服务的事实和显式承诺锁仍需遵守。现有 `pinned` 不是下一站锁。

单次计算仍不超过 1000 单、200 车，支持多个独立场景并发；历史事件和已完成工单归档，不无限堆入每次求解的地点矩阵。30 秒、120 秒、300 秒无改进三档保持原语义。实时业务的响应时间需要实测验收，不能把“30 秒搜索时限”当成从事件到生效的端到端时限。

## 2. 场景、事实、生效计划与求解任务

一个场景表示持续运营的调度范围；场景版本保存业务问题快照，执行版本保存车辆和工单事实，生效计划版本保存已确认安排。求解任务绑定这些版本及本次参数，结果只是候选方案。

```mermaid
flowchart LR
    E[新增单 / 完工 / 取消 / 车辆状态] --> S[持久化执行事实与业务版本]
    P[当前生效计划] --> C[编译剩余问题与锁定规则]
    S --> C
    C --> J[有界求解任务]
    J --> R[候选方案与变化说明]
    R --> V[按最新执行状态重新校验]
    V --> A[人工确认 / 配置自动采用]
    A --> P
```

需要区分以下版本，不能用一个“最新任务”指针替代：

| 对象 | 变化原因 | 对已有任务的影响 |
|---|---|---|
| 业务问题版本 | 新单、取消、时间窗、资源、约束变化 | 输入快照不变；需要重排时产生新任务 |
| 执行状态版本 | 出发、到达、开始/结束服务、装卸、故障等事实 | 旧候选可能过期，需要校验或重新求解 |
| 生效计划版本 | 人工或自动采用一个候选方案 | 作为后续稳定性比较和执行指令的基准 |
| 求解任务 | 某一组确定快照及参数的一次计算 | 有自己的排队、运行、停止、失败及结果记录 |

同一业务版本可以使用不同参数运行多个任务。`SubmitJobRequest.options` 和 `ReplanRequest.options` 支持逐任务替换参数，不因 30 秒改为 120 秒制造业务版本。

同一运营场景只能有一个生效计划，但可以有多个候选。启动运营时在 SQLite 事务中占用唯一非空 `resource_id`，关闭后释放；同一实际车辆不能跨场景重复运营，也不能在一个运营场景内以多个 Agent 重复出现。多天同车的静态场景应先准备本次运营的资源视图。REPLAY 场景使用独立模拟资源 ID。

## 3. 执行事实和状态转换

应用层记录稳定 ID、事件 ID、发生时刻、接收时钟、操作人和预期修订。SQLite 同时保存命令和物化快照；以 `expected_revision` 做并发控制，逐实体观测时间拒绝更早事实，相同事件 ID/完整内容返回首次快照。没有另设来源序号字段，调用方需在冲突后读取状态并核对再重试。

工单至少覆盖未开始、前往中、已到达/等待、服务中、已完成、已取消及异常。车辆至少覆盖可调度、行驶中、服务中、暂停、不可用，并记录当前位置及其时刻、当前任务、可再次出发时刻、实际载荷和货物归属。事实状态与“计划给谁做”分开：发布方案本身不能把工单标为已开始或已完成。

- 已完成事实不能通过普通场景编辑改写，也不提供覆盖完成事实的更正端点；现场错误完工的冲销流程属于后续扩展。服务未完成时可记录带原因的异常，再恢复剩余工作。
- 服务开始/结束使用实际上报时刻。`remaining_service_seconds` 有 presence：未报告时采用业务时长，明确报告 0 保留为 0；超时、提前完成和部分完成均基于实际上报，剩余时间到 0 不会自动制造完工事实。
- 已取消的未开始工单退出待执行集合；正在服务的取消、已装车货物的取消、车辆故障必须产生明确的业务处置，不能直接删除记录或凭空释放货物。
- 重复事件返回原处理结果；迟到事件不能覆盖更晚事实。缺少前置事件或事实矛盾时给出待处理冲突，不能猜测状态。
- 保存事件和标记“需要重排”应在同一事务中完成。队列满或服务重启不能丢失这个需求；恢复后用最新事实生成任务。

首版提供业务 API 和工作台手工回报入口，外部车载系统通过同一契约接入。模拟回放必须清晰标记，不能混入真实执行状态。

## 4. 从执行状态构造剩余问题

这部分由 vrp-1 应用/模型层负责；核心仍然只接收完整、不可变的计算输入，无 I/O、无全局状态。每次求解必须归档它实际使用的事实版本、当前时刻、矩阵、锁和生效计划基准。

### 时间与位置

可调度车辆从最后确认位置、当前时钟和可用时刻开始，而非早晨仓库。车辆观测时间独立保存，工作台显示其时刻；服务中任务按剩余秒数及流逝时间估计结束边界，必须由完成事件确认实际完工。临时位置产生的新边以请求的 fallback 参数估算，原有矩阵边保持原值，估算来源在结果中保留。当前没有 GPS 轨迹预测、自动离线判定或道路矩阵在线补精；外部系统应持续回报位置及累计驾驶秒数。

已完成前缀作为事实保留，优化未执行后缀。若前置工单已完成，后续工单的依赖约束仍需使用其实际完成时间及执行车辆；不能因移出待求解集合就丢失跨前缀/后缀的关系。

多前置依赖为 AND：规划时等待所有前置的预计完成，执行开始服务时则检查所有前置的实际完成事实。不同资源可以协作，不自动要求同资源。一个原子执行事件可以同时报告前置完成和后续开始；缺少任何一个前置的完成事实，整批事件拒绝，执行修订不前进。已在服务中或已完成工单的前置集合不可通过场景编辑改写。存在依赖时序违约的计划不能采用，人工接受业务违约也不能绕过该检查。

### 载荷与货物

静态输入仍按“该路线全部 DELIVERY 需求之和”计算出发载荷。实时输入使用 `ExecutedRoute.initial_load` 显式实际载荷，区分车载、待装、已卸和已取货物。运营启动时货物默认在仓库，已经装车的现场通过装货事件上报。

已覆盖货物归属、取消留车、完成取件增加载荷、回仓卸货、补货与交接。待装配送单生成 `@vrp/load/{id}` 访问及同车在先约束，取消留车/已取件生成 `@vrp/unload/{id}` 回程动作。计划装卸不改变实际库存；只有确认事件改变归属。交接必须停靠同一已知地点且货物未在服务中。首版按整单货物交接，不支持拆分数量或优化救援车会合点；故障时明确未派原因，由人工/业务系统确认交接后重排。

### 锁定与稳定性

锁定至少区分车辆归属、下一站、已承诺路线前缀、已承诺时间范围。已完成和服务中的事实不可由搜索修改；业务锁可由有明确操作记录的人工解除，但不能解锁已经发生的事实。

当前 `pinned` 只固定 `original_agent`，允许调整路线内顺序，保持既有含义。新的前缀与时刻约束需要单独契约和结构校验，所有构造、移动、扰动、k-opt 和初始解校验都必须遵守。

未锁定部分仍需控制改派、顺序变化和承诺时刻变化。热启动仅提供搜索起点，不能代替稳定性目标。以当前生效计划为基准定义这些代价，不能以每次新出现的候选方案不断重置基准。

### 全日累计与评分

`Problem.execution` 已携带实际载荷、已完成单数、驾驶/服务工作量、已配送量和固定费用支付事实。累计量进入上限和非线性均衡，行驶费用只计剩余路线。oracle、增量评分及数值上界同步实现，定义见 [constraints-v2.md](constraints-v2.md)。

不同问题/执行版本的总分不直接比较。采用前将当前生效计划剩余部分与候选方案放在同一最新事实、同一权重和同一矩阵下评估；历史执行指标独立展示。

## 5. 持续触发、任务资源与采用

业务事件触发重排，短时间连续事件合并；每个场景保留有界的待重排需求，避免一条定位上报创建一个任务。定位细节更新与改变可执行性的事件应区别处理。取消旧任务仍须等待子进程回收，不能提前释放资源额度。

若新单、完成、故障等使在算快照失效，标记旧候选过期，并安排最新快照；过期的继续优化结果可保留查看，但不得发布。合并窗口和最长等待时间应有上限，避免车辆持续上报导致永远无法产出方案。

采用必须是原子操作：

1. 获取最新业务、事实和生效计划版本，确认工单尚未执行/取消，资源仍归属本场景。
2. 重新投影、校验剩余方案；计算期间车辆继续移动、工单继续完成，不能冻结现实来配合旧结果。
3. 核对执行锁、货物、时间可达性及明确的采用策略；过期结果需要重新校验或重算，不能只因分数更好直接覆盖。
4. 按预期生效版本更新计划，保存差异、原因、来源任务、操作人/自动策略；并发采用只能有一个成功。
5. 产生带计划版本的执行指令变化，并记录接收/确认状态。车辆或业务端的旧确认不能覆盖新计划；传输失败支持幂等重试。

默认人工确认，自动采用需显式配置。采用时拒绝版本过期、结构锁、实际货物/容量、不可达边及承诺时间违约；其他业务 hard 违约只有人工提供原因后可接受。自动采用要求无 hard 违约，且不劣于同一当前事实下的原计划剩余部分；等分仅在计划已过期时刷新。`succeeded` 不等于可采用。工作台展示冲突和“计划待重新校验”。

去抖从第一条未处理事件计时，默认 250 ms、上限 5000 ms。GPS 单独更新不增加 `execution_version`，采用时按最新位置重算；业务、工单、货物、车辆状态/可用时间变化使旧候选过期。自动重排在额度允许时取消过时任务并提交最新快照；队列满保留 dirty 标记。禁用自动重排清除待自动提交标记，仍可手工重排。

求解共用机器级线程、进程、内存和队列预算。长时间搜索在子进程执行。已记录任务创建/开始/结束、搜索统计、采用时刻和车辆确认版本；尚未提供各阶段 P95 仪表盘，不能用搜索时限代替端到端 SLA。

## 6. 工作台首版闭环

工作台使用同一场景、任务和方案体系，已提供：

工作区与操作语义见 [workbench.md](workbench.md)。以甘特排程为主，点击工单/资源联动地图和详情；主入口区分继续优化、业务变化后的重新规划，以及执行事实驱动的实时重排。持续重排是事件自动触发策略，人工/自动采用是另一项独立策略。

- 场景导入、编辑、求解与比较，以及当前生效计划和候选方案的明确区分。
- 按车辆展示已完成前缀、当前行程/服务、锁定承诺、待执行后缀；实际时间与预计时间分开。
- 新增/取消工单、车辆故障、位置更新、开始/完成服务、装卸/交接等状态回报及冲突处理。
- 自动重排开关、人工确认/自动采用模式、改派/改序/时间变化和原因展示。
- 过期结果、手工暂停/故障车辆、待确认计划、未派工单与不可执行安排提示。
- 按事件回放场景演进，能定位每次输入、候选、采用和实际执行事实。

静态结果通过 `StartOperationRequest.initial_job_id` 原子校验、采用并启动执行。需要的装货访问进入计划，但实际装卸、出发和完工仍需事件确认。人工改派/改序通过 `AdjustPlan` 保留独立来源任务并重新评分；即使自动采用开启，这类人工候选也必须显式采用，恢复服务时同样如此。

地图首版可用示意连线；当前状态和可执行性不能依赖付费地图才能正确工作。真实轨迹与道路矩阵来源必须标明。

## 7. 首版验收清单与实施顺序

当前实现对应下面的协议、内核、服务和工作台阶段；自动化测试位于 `vrp-core/tests/execution.rs`、`vrp-server/tests/operations.rs`、HTTP 测试及 `scripts/smoke_workbench.py`。浏览器测试使用合成数据，截图和数据库输出到被忽略的 `corpus/ui-smoke-*`。没有声称真实动态运营回放或已达到生产吞吐目标。

1. **协议与规则**：执行事件、状态快照、任务参数、生效计划及锁的契约；明确时间、货物和累计评分语义。同步 engine/app proto 和评分文档。
2. **内核与模型**：剩余问题编译、锁保护、实际载荷、跨已完成前缀依赖、累计评分、稳定性；所有搜索策略覆盖，oracle/增量一致。
3. **服务闭环**：事件持久化、幂等/乱序、合并重排、过期检查、原子采用、确认/重试、恢复；保持多场景资源隔离和额度共享。
4. **工作台与发行**：上述操作流程、动态回放、部署包及端到端验收。前三项只完成 API 或内核时，不能宣称首版完整交付。

必须覆盖的事件序列：

| 场景 | 验收结果 |
|---|---|
| 出发后插入紧急单 | 从真实位置/可用时刻规划，遵守下一站策略，不移动服务中工单 |
| 取消尚未服务但已装车的配送单 | 不再上门，货物仍在车上，后续容量和回仓安排正确 |
| 车辆途中故障 | 不给故障车派新单，不凭空转移车载货物，明确救援/交接需求 |
| 服务超时、提前完成或部分完成 | 后续时间按实际进展更新，历史事实不改写 |
| 已完成前置单 + 未开始后续单 | 保留实际完成时间/原执行资源约束，不重新服务已完成单 |
| 求解中连续新增、完工、取消 | 合并触发不丢事件，旧结果不能覆盖新状态，最终得到最新候选 |
| 两名调度员同时采用 | 版本冲突明确，只有一个生效版本成功 |
| 重复/乱序事件与旧指令确认 | 不重复派单、不回退状态、不覆盖新计划 |
| 排队满、进程失败、服务重启 | 执行事实与生效方案保留，待重排需求恢复，运行任务可追溯 |
| 多场景并发和共享实际车辆 | 计算额度有界，生效计划不会重复占用同一资源 |
| 锁/货物/时间导致不可行 | 明确冲突和未派原因，不输出伪造的可执行方案 |

历史语料主要是静态请求/结果，只能验证导入、评分和静态方案。基于它构造的事件流需标为合成测试；真实动态验收还需要现场事件序列及期望行为，二者不能混称“历史连续求解回放”。
